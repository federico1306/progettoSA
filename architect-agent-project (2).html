Pillar 1

The council: peer architects, different minds

Common to all agents

  • Full architect mandate — not a specialist
  • Same question, same knowledge base
  • Same output contract (options, trade-offs, confidence)

Different for each agent

  • LLM — ≥3 model families (mandatory)
  • Stance — temperament & priorities (recommended)
  • Optional: temperature, reasoning depth

Why both? Different LLMs often still agree too quickly. Stances force real divergence before consensus.

Pillar 1 — suggested stances

Architect Agents: same job, different temperaments

⚙ Pragmatist

Simplest thing that works. Values time-to-market and team skills.

🛡 Guardian

Risk-averse. Values proven tech, reliability, security.

🚀 Innovator

Future-proof. Values evolvability and modern options.

🧐 Skeptic

Challenges every claim. Demands evidence and hidden costs.

Rules for the agents: reach own conclusion alone first • then share and debate • change mind only for an argument — see next slide.

Pillar 2

Debate protocol: from opinions to a proposal

Framechair sets context & QA scenarios
→
Proposeeach agent alone, no peeking
→
Critique & revisechallenge, update or defend
→
Convergevote / score / consensus
→
DecideADR + dissent
  • Think alone, then debate — LLMs tend to agree with whoever they talk to. Collaborating from the start gives instant, shallow agreement.
  • Bounded rounds — debate must always terminate.
  • Deadlock — chair tie-break or escalate to the human.
  • Keep the minority view — dissent is part of the output.

Pillar 2 — communication

Your architecture, your choice — within the rules

Free to explore (examples)

  • Any agentic pattern: orchestrator, peer-to-peer, hierarchical…
  • Blackboard / shared memory
  • Pub/sub message bus
  • Protocols: A2A, MCP for tools

Must be (non-negotiable)

  • Structured — typed message schema
  • Observable — visible live in the demo
  • Traceable — who said what, based on what
  • Swappable — add an agent without rewrites

Maximum freedom on patterns and topology, as long as every "must be" holds. Justify choices in ADRs.

Pillar 3

Feedback loop: the human decides, the council learns

Council proposes
→
Human reviewsfeedback + why
→
Council revisesnext iteration
→
Human decidesfinal decision
→
Agents learnfor future decisions

Short loop: one decision

Human feedback is used in the next debate round to improve the current proposal.

Long loop: all future decisions

The final human decision is stored and teaches the agents (e.g. memory, principles, per-model trust).

Goal: later decisions match the human's final choice more often — measured on slide 12.
